# OverlayManifest runtime integration: regie, atomic manifested install, gated ACK (v1)

The 0.10A cycle wires a parsed OverlayManifest all the way to pixels for the Video product. A pure cross-contract validator (`VideoOverlayManifestBridge`) binds a runtimeTrack to its manifest; `CloudTrackRepository` gains atomic same-revision runtime+manifest persistence and a manifested restore; an Android-free regie (`SceneRuntimeController`) decides when a scene shows or hides against a generation guard; `OverlayService` picks Case A (legacy `OverlayRenderer`) vs Case B (regie + `SceneRenderer`) per comment and owns a local-only asset seam; and `CloudControlClient` gains a `ManifestInstaller` seam so a manifested revision is ACK'd only after the full durable-install + scheduler + regie chain accepts. New bounded diagnostic codes carry manifest/scene outcomes without ever surfacing content. The ACK gating, atomic persistence, Case A/B exclusivity, generation guard, and no-network/no-dynamic-load boundaries hold and are exercised at pure JVM seams.

Watch for: Case B scenes are never expired by their own `durationMs` — the scheduler emits no expiry event and `onCommentExpired` has no production caller, so a manifested scene stays visible until the next due comment, eligibility loss, or teardown (confirmed). A re-delivered manifested assignment at `revision <= cached` is ACK'd without re-arming the regie (possible, low risk). Renderer visual drawing is unavoidably CI/physical-only, so the asset-walk/ordering seams are the only unit coverage of the render path (confirmed, by design).

**Verdict**: NEEDS_CHANGES

## High-level view

The design keeps the cross-contract rules in one pure place (`VideoOverlayManifestBridge`) and keeps `CloudControlClient` byte-only: it hands raw runtime+manifest JSON to a `ManifestInstaller` seam and never learns the Video coherence rules. The bridge enforces product/clock/source binding plus an exact comment↔scene bijection with integer-ms timing.

Atomicity lives in `CloudTrackRepository`: a manifested install validates, cross-checks, then commits revision+runtime+manifest in one editor commit, and a null manifest removes the stale key in the same commit. Both the legacy `save` and the manifested `save` strip or set the manifest key atomically, so a mixed revision (runtime rev N + manifest rev N-1) is unreachable through the repository. Restore is symmetric: `restoreWithManifest` fails closed and discards the whole revision if either half is corrupt, and refuses a non-manifested revision without clearing it so legacy `restore()` stays the Case A authority.

The ACK is gated by `OverlayService.installManifestedRevision`, a static Android-free core returning the armed revision only after durable install + scheduler load + regie arm all succeed; any failure returns 0 and the client throws before reaching the ACK POST. The ACK itself still sends `{revision, finalTrackId}` and fires strictly after install.

Case A/B exclusivity is a single deterministic predicate (`shouldUseSceneRenderer`): Case B is active only when the regie holds a manifest whose revision equals the active revision. The scheduler Listener consults it on every `onRender`/`onPlayback`, so one comment never drives both paths. A monotonic generation guard disarms late callbacks from a superseded revision.

The scene path is strictly local: `resolveLocalAsset` returns null (no transport this cycle), `SceneRenderer.preflight` probes only the local resolver and gates both the controller show and a direct `render` call, and the Python boundary asserts no URL/WebView/dynamic-class-load/transport-control over the scene sources. The one real gap is temporal: scenes have no `durationMs`-driven hide in Case B.

### Cross-contract validation isolated in the bridge

`VideoOverlayManifestBridge.validate` is the single owner of the section-5 rules and is kept out of `CloudControlClient`. It checks `product=="video"`, `clockMode=="media"`, and `sourceId.equals(runtimeTrack.trackId)`, then builds a by-id scene index (rejecting duplicate ids as `MANIFEST_INVALID`), requires equal cardinality (`MANIFEST_INCONSISTENT` otherwise), and for every comment requires a scene hit with exact `long ==` on both `startMs` and `durationMs`. Equal cardinality plus a hit for every comment id proves bijection with no extra scenes. Failures return a bounded `Result` carrying only a `ManifestCode`, never content, and the bridge has no ACK surface. `VideoOverlayManifestBridgeTest` runs the real parser and covers source mismatch, missing/extra scene, single-ms start and duration drift, and product/clock mismatch — these drive the actual logic rather than asserting constants.

### Atomic manifested persistence and fail-closed restore

`CloudTrackRepository.install` validates revision monotonicity and size caps, parses the runtime track and manifest, runs the bridge, and only on full success calls `storage.save(revision, runtime, manifest)` before `scheduler.load`. Any earlier failure returns an `InstallResult` with the bounded code and touches nothing durable, so the prior revision stays intact. The real `Storage.save(revision, runtime, manifest)` writes all three keys (or removes the manifest key) in one `commit`, and the legacy two-arg `save` was changed to `remove("manifest")` in the same commit — together these make a mixed revision unreachable: a Case A revision can never inherit a prior manifest, and a Case B commit is all-or-nothing.

```
install(rev,runtime,manifest)
  parse+bridge OK ──> storage.save(rev,runtime,manifest) [one commit] ──> scheduler.load ──> ok
  any failure      ──> prior (rev,runtime,manifest) untouched ──> bounded code, no scheduler change
```

`restoreWithManifest` requires a stored manifest; absent one it returns a failed result without clearing, preserving Case A for `restore()`. If a manifest exists but either half is corrupt it clears storage and returns `{false, 0, null}`, so a half or mixed revision never reaches the scheduler or regie. `CloudManifestCacheTest` proves atomic persist, same-revision restore of both halves, corrupt-manifest discard, invalid-new-revision non-replacement, the explicit no-mixed-revision case, cache-failure reporting, and legacy no-manifest behavior, all against a Memory storage double that mirrors single-commit semantics.

### ACK gated on the full install+arm chain

`installManifestedRevision` is the Android-free ACK-decision core: it installs atomically, records the bounded outcome into diagnostics, then re-reads the just-committed durable copy via `restoreWithManifest` and arms the regie with `replaceRevision`. It returns the armed revision only when install, scheduler load, and regie arm all succeed, and 0 on any failure. In `CloudControlClient`, a manifested assignment with no installer wired throws `PROTOCOL` (fails closed), and a failed install throws before the ACK POST — the ACK `{revision, finalTrackId}` is reachable only after the installer returns true. `ManifestInstallAckDecisionTest` drives this core directly: coherent install is ACK-able and arms the regie; inconsistent, invalid-contract, and non-durable installs each return 0 with the right bounded code and leave the prior revision byte-for-byte intact. This is the strongest evidence against the "ACK before durable+consistent install" risk — the ACK cannot fire first.

One reachable asymmetry: when `overlayManifest != null` but `revision <= cached`, the installer is skipped and the ACK still fires. For a genuine re-delivery of an already-installed revision this is a benign idempotent re-ACK, and on restart the regie was armed by `restoreWithManifest`. But the `activeRevision` field is only updated by the installer's success path and by restore; a manifested re-delivery that skips the installer relies on a prior restore having armed the regie for that revision. Worth confirming no path reaches this branch with the regie unarmed for the cached revision.

### Case A/B exclusivity and the generation guard

`shouldUseSceneRenderer(manifestLoadedRevision, activeRevision)` returns true only when `activeRevision > 0 && manifestLoadedRevision == activeRevision`, and `isSceneRendererActiveFor` additionally requires a loaded manifest. The scheduler Listener routes `onRender` to `sceneController.onCommentDue` and returns early when Case B is active, otherwise runs the unchanged legacy `showRenderer()` path; `onPlayback` forwards to exactly one path. So a single comment never drives both renderers. `onEligibility` always forwards to the controller (disarming a loaded manifest) and hides the legacy renderer only when Case A owns the comment — a deliberate asymmetry that avoids leaving either path visible.

The generation guard is the defense against stale callbacks: every load/unload/replace bumps `generation`, `onCommentDue(event, callbackGeneration)` ignores any event whose generation no longer matches, and `replaceRevision` drops the old visible scene before loading the new one. `onCommentDue` is also idempotent for the already-visible scene and enforces exactly-one-visual-scene by hiding any other scene first. `SceneRuntimeControllerTest` covers the matching show, unknown-id no-render, stale-generation ignore, replace-disarms-old, eligibility-loss-keeps-manifest, double-callback idempotency, ineligible suppression, preflight-false suppression, and null-safety against a recording fake that asserts `visibleCount <= 1`. These exercise the real guard logic.

### Case B scenes are never expired by their own duration

The scheduler's `Listener` has only `onRender`, `onPlayback`, `onEligibility` — there is no expiry callback. Legacy Case A works because `showTrackedCommentary(text, durationMs, bitmap)` hands the renderer the duration and the renderer self-expires via its own `postDelayed` countdown (freezing on pause for tracked cards). In Case B, `sink.show(scene)` calls `SceneRenderer.render(scene)` with no duration, and `SceneRuntimeController.onCommentExpired` — though implemented and tested — has no production caller anywhere in `OverlayService`. The scene's `durationMs`, validated exactly by the bridge, is dead data in the runtime path.

The consequence: once shown, a manifested scene is hidden only by the next due comment (replace), eligibility loss, a revision replace, or teardown. It does not disappear at the end of its own window the way Case A commentary does. For a track where comments are spaced apart, a scene stays on screen through the gap until the next one is due. This is a behavioral regression relative to Case A and should be closed before shipping — most directly by driving `onCommentExpired` from a scheduler-side expiry signal (media-position driven, not a second clock), so scene expiry stays under the existing temporal authority.

This also hollows out the section-12 freeze claim for Case B: `onPlayback` correctly records state without adding a clock, and the pause test proves nothing drains a scene's duration — but that is because nothing drives scene expiry at all, so "freeze keeps the qualified behavior" has nothing to freeze.

### Local-only asset seam and no-network scene path

`resolveLocalAsset` returns null for every reference this cycle, so there is no download/CDN/HTTP path; the comment on the seam documents the absent transport. `SceneRenderer.preflight` walks every IMAGE `assetRef` (recursing groups) and returns false if any does not resolve locally, catching resolver faults as a bounded false rather than a crash. The controller gates `show` on preflight and records `SCENE_ASSET_UNAVAILABLE` on failure; `render` also calls `preflight` itself so a direct caller cannot get a partial render. A missing asset is correctly a `SceneCode` (scene failure), not a `ManifestCode` (manifest inconsistency), matching section 19. The pure `imageAssetRefs` and `orderedForTest` seams are unit-tested for group recursion, declared order, text-only no-requirement, null-safety, and deterministic zIndex-then-id ordering. The actual View construction in `render`/`build*` cannot be unit-proven (default-value stubs) and remains CI/physical — the one unavoidable coverage gap on the render path.

### Bounded diagnostics and preserved boundaries

`ManifestCode {NONE, MANIFEST_INVALID, MANIFEST_INCONSISTENT, MANIFEST_CACHE_FAILED}` and `SceneCode {NONE, SCENE_ASSET_UNAVAILABLE, SCENE_RENDER_FAILED}` are bounded enums surfaced through `DiagnosticsStore`/`RuntimeDiagnostics`, carry no content, and never gate logic. `clearRuntimeSignals` resets both. No gradle, AndroidManifest, or signing files changed; the Python boundary extends the forbidden-token and permission-set assertions over the new regie and bridge sources and asserts `CloudControlClient` holds no graphics tokens and `SceneRenderer`/controller hold no Cloud tokens. The only CI config change is adding the new branch to `android-debug.yml` push triggers, documented as temporary. All existing boundary tests are retained.
